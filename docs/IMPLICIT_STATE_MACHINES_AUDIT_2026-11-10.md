# Audit state machine aplikasi — 10 November 2026

Audit statis terhadap jalur aplikasi lokal. Ini bukan bukti skema/deployment produksi. “Implisit” di sini berarti fase atau transisi dibentuk dari beberapa boolean, nilai kosong, dan status yang diperiksa tersebar; “eksplisit” berarti daftar transisi/hasil atau kontraknya sudah dipusatkan. Peta ini mencakup mesin bisnis dan lifecycle layar yang ditemukan pada `src/`, `api/`, `server/`, dan `migrations/`.

## Ringkasan

- Mesin bisnis kritis sudah punya sebagian guard eksplisit: transisi order dan integritas lintas order/laporan/invoice/pembayaran di `src/lib/sfmIntegrity.js`; alokasi pembayaran WhatsApp dan status pengiriman di `src/lib/waOperations.js`; RPC/outbox transaksional di migrasi WhatsApp; dedup webhook dan retry media di backend.
- Risiko sisa utama berada di batas antarmesin: status turunan yang legacy, UI yang menyimpulkan “kosong” dari data belum dimuat, beberapa `loading/error/ready` terpisah, dan hasil eksternal yang belum pasti. Status HTTP 200 atau status gateway bukan bukti transaksi/pesan telah selesai.
- Perbaikan pada audit ini: inbox membedakan polling awal, kegagalan sebelum ada snapshot, data kosong setelah sukses, dan data lama saat refresh gagal; riwayat outbox memakai fase `loading | ready | error` yang menyimpan snapshot bersama fase. Perluasan audit 10 November juga memperbaiki lifecycle portal pelanggan, katalog WhatsApp/ARA, inventaris alat kantor, dan harga AC. Error atau loading pada daftar tersebut tidak lagi disamarkan sebagai hasil kosong; tindakan review ARA dikunci ketika snapshot belum dapat dipastikan. Tidak ada perubahan DB, pembayaran, webhook, cron, atau deploy.

## Temuan diperbaiki

### Inbox dan riwayat pengiriman WhatsApp

Polling inbox sebelumnya menggunakan `loading`, `error`, dan `updatedAt`, tetapi empty state tidak membaca ketiganya. Karena itu request pertama yang belum selesai atau gagal dapat terlihat seperti inbox yang benar-benar belum pernah menerima pesan. Header juga selalu menyebut data terakhir tetap tampil walaupun belum ada snapshot sukses.

`src/views/WaPanel.jsx` kini menggunakan `updatedAt` sebagai penanda snapshot sukses: tanpa snapshot, loading dan unavailable punya pesan/role aksesibilitas tersendiri; setelah sukses, hasil kosong berarti kosong yang terverifikasi; jika refresh berikutnya gagal, snapshot sebelumnya tetap ditampilkan dan disebut sebagai data terakhir.

Sebelumnya `history`, `historyReady`, dan `error` hidup terpisah. Saat query riwayat gagal, `historyReady` tetap false dan `history` tetap kosong, tetapi UI tetap menampilkan kalimat kosong “Belum ada riwayat pengiriman terpantau.” Itu menyamarkan keadaan tidak diketahui sebagai keadaan kosong.

Sekarang `historyState` menyimpan `phase`, `rows`, dan `error` bersama-sama di `src/views/WaOperationsPanel.jsx`. UI membedakan loading, error, dan hasil kosong. Tombol kirim dokumen/pengingat tetap nonaktif sampai pembacaan sukses, sehingga audit status lama tidak dilewati.

## Batas audit dan langkah aman berikutnya

Peta ini menginventarisasi lifecycle yang tersimpan, diturunkan, atau memengaruhi tindakan pengguna pada jalur aplikasi. Ada banyak state presentasi sederhana (tab, modal, filter) yang bukan mesin bisnis mandiri; state itu tetap perlu lifecycle yang benar bila menyimpan request asynchronous. Pemeriksaan ini tidak menjalankan request ke layanan luar dan tidak mengklaim schema atau produksi sama dengan checkout lokal.

Prioritas refactor lanjutan yang aman adalah mengubah satu lifecycle UI per perubahan dan menjaga kontrak state bisnis/DB tetap sama: (1) gunakan union fase untuk async read snapshot yang kritis, (2) pusatkan enum/transisi sebelum menambah status baru, (3) dokumentasikan aktor dan efek samping tiap transisi, (4) verifikasi komponen serta jalur server terkait sebelum rilis. Tidak ada klaim semua komponen telah direfactor; audit mencatat mesin lintas-domain dan memperbaiki inkonsistensi konkret yang ditemukan tanpa memperluas cakupan transaksi.

## Perluasan audit statis dan perbaikan lokal — 10 November 2026

Pemeriksaan tambahan menelusuri state asynchronous UI pada `src/views`, `src/components`, `src/hooks`, dan `src/project`, lalu mencocokkan boundary API/domain pada `api/`, `server/`, dan migrasi. Temuan berikut dapat dibuktikan langsung dari implementasi lokal:

| Lifecycle | Sebelum | Perubahan | Dampak yang dijaga |
|---|---|---|---|
| Portal pelanggan (`src/views/CustomerPortalView.jsx`) | Status data, `loading`, dan `error` terpisah. Saat token prop berubah, isi token sebelumnya dapat tetap dirender selama request berikutnya; respons lama juga dapat menang setelah token baru. Respons HTTP gagal tanpa body `error` bisa masuk jalur sukses. | Fase `loading | ready | error` menyimpan payload bersama error; token baru membersihkan data turunan, response `ok` diperiksa, dan efek lama dibatalkan. Voucher tetap bersifat tambahan dan tidak mengubah hasil utama portal. | Tidak menampilkan detail pelanggan dari token sebelumnya dan tidak menganggap respons HTTP gagal sebagai data berhasil. |
| Inventaris alat kantor (`src/views/OfficeToolsView.jsx`) | Hasil Supabase tanpa data/error tidak diperiksa; dua kegagalan baca bisa terlihat sebagai inventaris kosong. | Error dua query ditampilkan, snapshot sebelumnya dipertahankan, empty state hanya tampil saat pembacaan sukses, dan tersedia retry. | Tidak menyimpulkan stok/alat kosong saat dependency gagal. |
| Harga unit AC (`src/views/PriceListView.jsx`) | Query error hanya memberi notifikasi, lalu state kosong membuat tabel tampak benar-benar tidak punya harga. | Error disimpan bersama fase tampilan, empty state ditahan sampai query sukses, dan ada retry. | Owner tidak terdorong menyimpulkan item tidak ada atau menambah duplikat karena kegagalan baca. |
| Katalog WhatsApp (`src/views/WaCatalogView.jsx`) | Error baca katalog tampil bersamaan dengan teks “Belum ada item”. | Fase katalog eksplisit; empty state hanya tampil sesudah load berhasil dan hasil memang kosong. | Hasil error tidak diterjemahkan menjadi katalog kosong. |
| Review ARA (`src/views/AraReviewPanel.jsx`) | Render awal dapat mengatakan belum ada draf sebelum query pertama selesai; refresh gagal mempertahankan baris lama tanpa menandai snapshot stale, dan aksi tetap aktif. | Fase `loading | refreshing | ready | error` membawa snapshot; refresh gagal menandai snapshot stale, empty state hanya setelah sukses, dan aksi review nonaktif ketika data belum dapat dipastikan. | Draft lama tidak diproses sebagai keadaan terkini setelah kegagalan baca. |
| Draft ARA lintas percakapan (`src/views/AraReviewPanel.jsx`) | Pergantian nomor telepon dapat merender sesaat draf nomor sebelumnya sebelum efek pemuatan dimulai. | Snapshot membawa kunci `phone`; render langsung menahan data sampai scope cocok dan hanya mempertahankan snapshot untuk nomor yang sama. | Draf dan jawaban pelanggan tidak tertukar saat staf berpindah percakapan. |

Audit statis ini sudah menginventarisasi kelompok mesin bisnis dan lifecycle layar pada tabel di atas, tetapi tidak mengubah semua boolean presentasi menjadi reducer/union. Sebagian besar `saving/busy` adalah guard operasi tunggal yang valid, sedangkan refactor massal berisiko mengubah urutan efek atau kontrak domain tanpa manfaat pengguna yang terukur. Perubahan saat ini dibatasi pada lifecycle yang membingungkan keadaan kosong/gagal atau dapat menampilkan snapshot lintas-token. Tidak ada request runtime eksternal, skema produksi, atau perilaku transaksi yang diverifikasi/diubah dalam pekerjaan ini.
