# Patch FSM: authorization, invoice transactions, stock and split teams

Prepared 15 November 2026. Release integration into current main; production rollout status is recorded separately from local test results.

## Scope and behavior

| Area | Implementation |
|---|---|
| SQL authorization | Migration 246 explicitly rejects missing JWT/user/application roles in settlement, partial-payment and order-edit RPCs; PUBLIC/anon EXECUTE is revoked. Migration 248 additionally closes the NULL application-role gate in expense-to-stock linking and checks caller context in the six stock RPCs. Existing role allowlists and signatures are retained. |
| Invoice reversal/deletion | Migration 247 adds atomic RPCs and database invariants. **Owner chose to preserve posted cash and block resets**, not create refunds or erase journal entries. Positive PAID legacy invoices are protected even without detailed receipts. Unposted zero-value status correction remains atomic with its order updates. Unpaid/unposted invoice deletion is atomic; posted invoices and payment logs are retained. |
| Approval | One RPC locks and approves the actual invoice and owning order, preserves balances, checks expected updated_at, and reads the final balance after deposit triggers. UI state, success logs and modal closure follow confirmed success only. |
| Inventory | Migration 248 uses relative aggregate updates, statement-level inventory serialization and the same early lock in six existing row-locking RPCs. This protects physical-unit SUM mirrors, first-unit transitions and SKU moves as well as ordinary movements. The existing policy allowing visible negative aggregate stock is preserved; physical-unit CHECK(stock>=0) remains. |
| Multi-team | Migration 249 validates the whole request, client/unit ownership and unique allocation, then inserts every order and reserves every specified technician/helper in one transaction. A payload-bound receipt supports retries and rejects changed payloads. Raw split INSERTs from older clients are denied by an invoker trigger; a caller-set GUC alone cannot bypass it. |
| Frontend | RPC-only invoice wrappers; no direct payment fallback on missing RPC; no optimistic approval/group success. A bounded command wait does not automatically replay mutations. Split intent IDs survive a lost response/reload in browser session storage, scoped by actor and hashed payload; only the UUID is stored. |

The migration bodies create/replace functions and triggers and add one NOT VALID FK. **They do not drop tables/columns, alter ledger columns, delete historical receipts, rewrite balances, validate historical dangling references, or repair old transactions during application.** The DELETE inside the new invoice command is invoked only when an authorized operator explicitly deletes an unposted invoice.

SQL functions execute within the transaction of the RPC request. An exception rolls back the command; COMMIT/ROLLBACK must not be placed inside the function body. Each migration file also has its own BEGIN/COMMIT wrapper. See [Supabase database functions](https://supabase.com/docs/guides/database/functions) and [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html).

## Metadata and safeguards

Actual production columns, defaults, generated-column flags, selected constraints and functions were captured **read-only on 15 November**, PostgreSQL 17.6, with no business rows copied. The metadata-only test fixture is [fsm-hardening-schema-20261115.json](../scripts/fixtures/fsm-hardening-schema-20261115.json).

Migrations 246/248 contain fingerprint preflights for the existing function bodies they replace. They accept the captured definition or the tested patched definition. If the database has changed, the migration fails before overwriting that logic. **Do not remove the check to force it through**; capture and review the changed function and forward-port the patch. Fingerprints are recorded in [function-fingerprints.json](../deliverables/fsm-fixes-2026-11-15/function-fingerprints.json).

The new order→invoice FK is NOT VALID: historical dangling links remain untouched, but new links must reference a real invoice. Validation and historical repair are separate reviewed work.

Payment-protection behavior intentionally applies to old browser tabs too. They cannot delete a payment log, detach a paid invoice link, reset a paid balance, or delete a report before its billing/stock dependencies. Deleting reports with invoice/stock history is blocked pending a dedicated cancellation workflow; it does not attempt a partial material return. Refresh old tabs after deployment to use the atomic team command. Normal report submission, reads and payment recording are not disabled by these guards.

Inventory writes intentionally serialize behind a short transaction lock. Six existing stock RPCs acquire it before their row locks, and statement triggers protect direct mutations. Lock waits are bounded to 5 seconds at these boundaries. This is a correctness-first tradeoff, **not a production throughput benchmark**. Future stock writers must use the same ordering. Never blindly replay an inventory command after a lost response; inspect its persisted result first.

## Manual rollout

1. Review the exact source diff and migration definitions against the current deployment branch. Confirm a usable current backup and run the patch on a production-compatible staging schema first. No fresh production export is required by this patch itself.
2. Verify the schema prerequisites and function fingerprints. Use the owning database role for the existing functions/tables (normally postgres), or an authorized administrator. Do not broaden authenticated grants to make a migration run.
3. Apply complete migration files 246→247→248→249. With psql use `-X -v ON_ERROR_STOP=1`; in Studio run the entire file. A lock timeout or definition-drift error means stop and review; do not apply a truncated file or bypass the guard. In an interactive aborted transaction, issue ROLLBACK before retrying.
4. Deploy the reviewed application changes **after** those RPCs exist. Missing RPCs fail closed; the application does not fall back to unsafe direct writes. Ask operators to refresh old tabs for split creation. Do not rerun 235/236 to deploy this patch.
5. Verify actual Coolify image/source SHA and database definitions separately. The old health marker alone does not prove release identity. The supplied [verify-readonly.sql](../deliverables/fsm-fixes-2026-11-15/verify-readonly.sql) checks catalog state without changing business data.
6. In staging, exercise Owner/Admin/Finance approval/payment, field/inactive denial, helper conflicts, failed group member, posted-invoice reset/deletion denial and physical stock mirror. Check special deposit/withholding/grouped invoices with the full production trigger graph before production acceptance. Use controlled authorized fixtures for any production mutation checks.

A web redeploy does not execute SQL migrations. Rolling back application code does not remove these safety guards; old unsafe writes may be denied. Prefer a forward correction and keep posted-payment protections. Do not revert to the old read-then-set stock function or a paid_amount reset.
